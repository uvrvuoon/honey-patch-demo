## 2. 결과 요약 (Windows 11, Python 3.14.5, 커밋 63713b0)

| 실행 모드 | 결과 |
|---|---|
| 기본 (서버 ③ 한 번만 띄우고 10개 연속) | **29/30 일치** — E3 1건 불일치 |
| `--fresh` (사례마다 서버 ③ 새로 실행) | **30/30 일치** |

**핵심: 표기를 바꿔도 세 서버의 판정은 흔들리지 않았다.**

- 같은 공격을 5가지 모양(`..\`, 1회 인코딩, 대문자 16진수 인코딩, 대소문자, 절대 경로)으로 보냈을 때
  → ①은 **5건 모두 진짜 비밀번호 3개 유출**, ②는 **5건 모두 403**, ③은 **5건 모두 가짜 파일 + 진짜 비밀 0개**
- 2중 인코딩(E3)은 우회가 아니라 그냥 없는 파일 이름이 되어 404 (서버가 인코딩을 한 번만 해제하므로)
- 빈 값·널 바이트는 경로 판정 전에 400
- `..`가 들어 있어도 결국 public 안이면 정상 처리(E8) → **오탐 없음**

## 3. 반례 1건과 분류

| 번호 | 입력 | 기대 결과 | 실제 결과 | 분류 | 처리 |
|---|---|---|---|---|---|
| E3 | `%252e%252e%252fsecret%252fpasswords.txt` (서버 ③) | 404 · 공격 아님이므로 **미끼 전환 아니요** | 404 · **미끼 전환 예**(로그에 줄이 생김) | **시험 설계 결함**(구현 버그 아님) | `--fresh` 모드 추가, 두 결과 모두 기록 |

**원인**: 서버 ③은 한 번 공격한 IP를 기억했다가(sticky) 그 IP의 이후 요청에도 로그를 남깁니다(README 6절 명세대로). E3 직전 사례 E2가 같은 공격자 IP로 공격이었기 때문에, E3는 공격이 아닌데도 `sticky` 로그가 남았습니다. 서버는 명세대로 동작했고, **"사례마다 서버가 새로 뜬다"고 가정한 제 기대값이 틀렸습니다.**

규칙대로 기대값은 고치지 않았고, 대신 사례마다 서버 ③을 새로 띄우는 `--fresh` 모드를 만들어 다시 돌렸습니다(30/30 일치). 두 결과 파일을 모두 저장소에 남겼습니다.

**배운 점(보고서에 쓸 만한 것)**: 추가 사례를 한 서버에 연달아 보내면 **앞 사례가 뒤 사례의 결과를 바꿉니다.** 상태(IP 기억)를 가진 방어를 검증할 때는 사례마다 상태를 비워야 합니다. 안지민의 XFF 스크립트가 시나리오마다 서버를 새로 띄운 것과 같은 이유입니다.

## 4. OS에 따라 결과가 갈리는 입력 (TA 지적 사항)

12주차 피드백에서 TA가 우리 팀 반례 후보로 "**OS별 경로 구분자(`..\`) 처리 차이**"를 적었습니다. 스크립트는 실행 환경의 두 속성을 시작할 때 확인해, 그 조합에 맞는 기대값 표를 고릅니다(결과를 보고 고르는 것이 아니라 미리 갈라 둔 표를 고르는 방식).

| 속성 | Windows | Linux | macOS(기본 APFS) |
|---|---|---|---|
| `\`가 경로 구분자 | 예 | 아니요 | 아니요 |
| 파일 시스템 대소문자 구분 | 아니요 | 예 | 아니요 |

**세 환경에서 모두 실행해 확인했습니다** (셋 다 기대와 30/30 일치 — 스크립트가 환경에 맞는 기대값을 쓰기 때문):

| 번호 | Windows 11 / Py 3.14 | macOS / Py 3.15 | Linux(WSL Ubuntu 22.04) / Py 3.10 |
|---|---|---|---|
| E1 `..\secret\passwords.txt` | ① 200 유출 / ② 403 / ③ 200 가짜 | **셋 다 404** | **셋 다 404** |
| E4 `../SECRET/PASSWORDS.TXT` | ① 200 유출 / ② 403 / ③ 200 가짜 | ① 200 유출 / ② 403 / ③ 200 가짜 | ① 404 / ② **403** / ③ **404** |

결과 파일: `tests/results/encoding_results_fresh.md`(Windows) · `_macos.md` · `_linux.md`

읽는 법:

- **E1**: Windows만 `\`를 폴더 구분자로 보기 때문에 **Windows에서만 경로 이탈이 성립**합니다. macOS·Linux에서는 `..\secret\passwords.txt` 전체가 하나의 파일 이름이라 그냥 없는 파일(404)입니다.
- **E4**: 파일 이름 대소문자를 구분하는 **Linux에서만** ①이 404가 되고, ③도 대문자 이름에 맞는 가짜 파일을 못 찾아 404가 됩니다. 이때 ②는 403이라 **②와 ③의 응답 코드가 갈립니다.**

**→ 같은 입력이 OS에 따라 다르게 판정되는 것이 세 환경 실측으로 확인되었습니다.** 분류는 **명세상 미지원** — OS별 경로 규칙 차이를 다루지 않기로 했고 README 6절에 적혀 있습니다. 어느 OS에서도 진짜 비밀이 ②③으로 새지는 않지만, **재현 결과가 환경마다 다르게 보이는 것**이 한계입니다. Linux의 E4에서 ②③이 갈리는 것은 **이수빈이 기록한 "미끼 없는 파일 공격 → ③이 404"와 같은 메커니즘**입니다.

(Linux의 E4가 ② 403 / ③ 404로 갈리는 건은 이수빈 항목과 같은 메커니즘이라 별도 반례로 올리지 않고 그 항목을 참조합니다.)

## 5. 부록 — 실행 전에 적어 둔 기대값 전문

아래 표는 **스크립트를 한 번도 돌리기 전에** 작성한 기대값입니다(2026-11-26).
코드에서는 `tests/test_encoding_cases.py`의 `expectations()` 함수에 같은 내용이 들어 있고,
실행할 때마다 `tests/results/encoding_results.json`의 `expect` 항목으로 결과와 함께 저장됩니다.

| 번호 | 입력 (`file=`) | ① 기대 | ② 기대 | ③ 기대 |
|---|---|---|---|---|
| E1 | `..\secret\passwords.txt` | 200 진짜 유출(3개) | 403 | 200 가짜 · 미끼 예 |
| E2 | `%2e%2e%2fsecret%2fpasswords.txt` | 200 진짜 유출(3개) | 403 | 200 가짜 · 미끼 예 |
| E3 | `%252e%252e%252fsecret%252fpasswords.txt` | 404 | 404 | 404 · 미끼 **아니요** |
| E4 | `../SECRET/PASSWORDS.TXT` | 200 진짜 유출(3개) | 403 | 200 가짜 · 미끼 예 |
| E5 | `<절대경로>/data/secret/passwords.txt` | 200 진짜 유출(3개) | 403 | 200 가짜 · 미끼 예 |
| E6 | (빈 값) | 400 | 400 | 400 · 미끼 아니요 |
| E7 | `public/../public/report.txt` | 404 | 404 | 404 · 미끼 아니요 |
| E8 | `../public/report.txt` | 200 공개 | 200 공개 | 200 공개 · 미끼 아니요 |
| E9 | `report.txt%00.png` | 400 | 400 | 400 · 미끼 아니요 |
| E10 | `%2E%2E%2Fsecret%2Fpasswords.txt` | 200 진짜 유출(3개) | 403 | 200 가짜 · 미끼 예 |

위 표는 `\`가 경로 구분자이고 파일 시스템이 대소문자를 구분하지 않는 환경(Windows) 기준입니다.
다른 환경의 기대값은 4절과 `expectations()` 함수의 분기에 있습니다.

**실행 후 바뀐 것은 없습니다.** E3 ③에서 "미끼 아니요"로 적어 둔 것이 실제로는 "예"로 나왔고,
기대값을 고치는 대신 3절처럼 원인을 분석해 기록했습니다.
