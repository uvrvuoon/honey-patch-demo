# 14주차 실험 계획 — 가짜 파일 수에 따른 서버 ③ 응답 시간

담당: 윤아란 · 작성: 2026-11-24 · 스크립트: `tests/make_decoys.py`, `tests/bench.py`

## 1. 실험 질문

미끼 폴더의 가짜 파일 수가 늘어나도 서버 ③(허니패치)의 응답 시간이 변하지 않는가?

- 원논문은 공격을 감지하면 미끼 환경으로 옮기는 데 드는 비용(메모리 치환, 프로세스 복제)을 측정했다. 본 구현에는 그 단계가 없고, 요청 경로를 미끼 폴더의 같은 위치로 바꿔 파일 하나를 읽는다(`decoy_path()`).
- 그래서 가짜 파일 수와 응답 시간은 **관계가 없을 것**으로 예상한다. 예상대로라면 "미끼를 많이 늘려도 비용이 늘지 않는다"는 결과가 되고, 다르게 나오면 원인을 분석한다.
- 원논문 수치와 직접 비교하지 않고, 같은 조건에서 변수만 바꾼 결과를 비교한다(13주차 안내).

## 2. 설계

| 항목 | 내용 |
|---|---|
| 변수 (하나) | `data/decoy/secret/`에 추가한 가짜 파일 수: **10 / 100 / 1000** (기본 미끼 `passwords.txt` 1개는 항상 유지) |
| 고정 조건 | 서버 ③만 측정, 로컬(127.0.0.1), 같은 PC·같은 커밋, 다른 프로그램 최소화 |
| 지표 | 서버 ③ 응답 시간(ms): 요청 전송부터 응답 본문 수신까지 (`time.perf_counter`) |
| 보조 지표 | 이상 응답 수: 상태 코드나 응답 내용이 기대와 다른 횟수 (속도만 보고 동작이 바뀐 걸 놓치지 않기 위함) |
| 요청 3종 | 정상 `report.txt` (10.0.0.10) / 공격 `../secret/passwords.txt` (10.0.0.66) / 공격후정상 `report.txt` (10.0.0.66) |
| 반복 | 조건·요청별 **200회** 측정, 앞의 **5회는 워밍업으로 버림**, 전체를 **3라운드** 반복 |
| 순서 효과 차단 | 라운드마다 조건 순서를 섞음(시드 14 고정), 조건마다 서버 ③을 새로 실행(공격자 기억 초기화) |
| 대표값 | **중앙값**. 순간적으로 튀는 값(예: 15ms)에 평균이 끌려가므로 중앙값을 쓰고, 평균·p95·최소·최대·표준편차는 함께 기록 |
| 판정 기준 | 조건 간 중앙값 차이가 **라운드 간 중앙값 흔들림보다 작으면** "차이 없음"으로 판단 |

### 기대 결과 (실행 전 작성)

| 가짜 파일 수 | 정상 | 공격 | 공격후정상 | 이상 응답 |
|---|---|---|---|---|
| 10 / 100 / 1000 | 조건 간 차이 없음 | 조건 간 차이 없음 | 조건 간 차이 없음 | 0 |

- 공격 응답은 항상 가짜 `passwords.txt`, 정상·공격후정상은 항상 공개 `report.txt`여야 한다.

## 3. 실행 조건 기록

`bench.py`가 결과 파일 맨 위에 자동으로 기록한다: 실행 시각, OS, CPU 수, Python 버전, 커밋 해시(서버 코드 수정 여부 포함), 실행 명령어, 변수·반복 설정.

## 4. 실행 방법

```bash
git pull                                  # 버그 수정 반영된 최신 코드로 측정
python tests/bench.py                     # 10/100/1000 × 200회 × 3라운드 (Windows는 py)
```

- 서버를 미리 켤 필요 없음 (스크립트가 빈 포트로 서버 ③을 띄우고 끔)
- 끝나면 생성 파일(`gen_*.txt`)을 지우고 `logs/honeypatch.log`를 실행 전 상태로 되돌림
- 결과: `tests/results/bench.md`(보고서용 표), `tests/results/bench.json`(원자료 전체)
- 가짜 파일만 따로 만들고 지우기: `python tests/make_decoys.py --count 100` / `--clean` / `--status`

## 5. 반복 횟수를 정한 근거 (시험 실행)

시험 실행(50회 × 2라운드, Claude 작업 환경의 Linux, Python 3.13)에서:

- 전체 소요 1.6초 → 기본 설정(200회 × 3라운드)도 10초 안팎이라 횟수를 늘려도 부담이 없음
- 같은 조건의 라운드 간 중앙값 차이가 최대 약 0.15ms로, 조건 간 차이와 비슷한 크기였음 → 50회로는 흔들림과 차이를 구분하기 어려워 200회 × 3라운드로 정함
- 한 번씩 15ms 같은 튀는 값이 있어 평균보다 중앙값을 대표값으로 정함
- 이상 응답 검출 확인: 서버 ③이 공격에 진짜 파일을 주도록 일부러 바꿔 돌렸을 때 공격 10/10회가 이상 응답으로 잡힘(원상복구함)

- 팀 PC의 Linux VM(Windows 폴더 공유)에서 소규모 실행(10·20개 × 10회): 이상 응답 0, 정리·로그 복구 정상. 다만 공유 폴더의 파일 쓰기가 느려 응답 시간이 10~30ms로 부풀고, 1000개 생성은 3분 안에 끝나지 않음 → **본 측정은 Windows에서 `py tests/bench.py`로 직접 실행**
- 이 VM 실행에서 공격·공격후정상(로그 기록 있음)이 정상(로그 없음)보다 느렸음 → 본 측정에서 로그 쓰기 비용으로 해석 가능한지 확인

※ 시험 실행 수치는 Claude 작업 환경 결과다. **14주차 본 측정은 팀 PC에서 다시 실행**하고 그 결과만 보고서에 쓴다.

## 6. 한계 (미리 기록)

- 로컬 측정이라 네트워크 지연이 없음 → 실제 공격자가 원격에서 시간 차를 볼 수 있는지와는 다름
- 미끼를 경로 매핑으로 바로 찾는 구조라 파일 수의 영향이 거의 없는 것이 설계상 자연스러움. 원논문의 지연(약 0.25초)과는 비교 대상이 아님
- OS의 파일 캐시 영향은 워밍업으로 줄였지만 완전히 없애지는 못함
