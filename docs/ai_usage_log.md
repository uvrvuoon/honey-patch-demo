# AI 사용 기록

주간 보고서의 "AI 활용 기록" 항목에 쓰는 기록입니다. 취합: 이수빈.
AI를 쓸 때마다 **본인 이름 절 아래에** 한 건씩 추가해 주세요. 매주 1건 이상.

작성 요령
- **요청 내용**: AI에게 실제로 보낸 요청을 한두 문장으로. (예: "`..`가 들어오면 403을 내도록 고쳐 줘")
- **결과 확인 방법**: AI가 준 코드를 어떻게 검증했는지. 검증 사례 3개(정상·위반·경계) 실행 결과를 적으면 가장 좋음
- **채택·수정한 부분**: 그대로 쓴 것, 고친 것, 버린 것과 그 이유
- **막힌 점**: AI가 틀렸거나 오래 걸린 부분 (보고서의 한계·배운 점에 그대로 씀)

## 이수빈

### 11/18 (수) — 비교 웹 화면 첫 버전

| 항목 | 내용 |
|---|---|
| 도구 | Claude |
| 요청 내용 | 원논문, 구현 명세, 작업 계획, 저장소 링크를 주고 "비교 웹 화면 구성 작업을 시작해 줘"라고 요청 |
| 결과 | `web/app.py`(세 서버에 같은 요청을 동시에 보내 결과를 모아 주는 비교 서버, 포트 8000), `web/index.html`(3칸 비교 화면, 미끼 방 감시 기록, 요청 기록 표) |
| 결과 확인 방법 | 서버 ①②와 테스트용 임시 ③을 띄우고 검증 사례 3개를 화면과 `/api/compare`로 실행. 정상·경계는 세 서버 모두 공개 파일, 위반은 ① 진짜 유출(진짜 비밀번호 3개) / ② 403 / ③ 가짜 파일·진짜 비밀번호 0개·미끼 전환 "예"로 기대 결과표와 일치 |
| 채택·수정한 부분 | 브라우저가 8001~8003에 직접 요청하면 CORS로 막혀서, 다른 팀원 서버를 고치지 않고 비교 서버가 대신 요청하는 구조를 채택. 기존 서버처럼 표준 라이브러리만 사용(명세의 Flask 대신). ③이 꺼졌을 때 "미끼 이동: 아니요"로 잘못 보이던 것을 "해당 없음"으로 수정 |
| 막힌 점 | 화면이 모든 요청을 같은 IP(127.0.0.1)로 보내므로, ③이 IP로 공격자를 기억하면 공격 후 정상 요청까지 미끼로 갈 수 있음 → 정상 사용자 10.0.0.10, 공격자 10.0.0.66을 `X-Forwarded-For` 헤더로 구분해 보내도록 함. ③이 이 헤더를 읽어야 하므로 안지민과 맞춰야 함 |

### 11/24 (화) — 14주차 실험 계획과 측정 스크립트

| 항목 | 내용 |
|---|---|
| 도구 | Claude |
| 요청 내용 | 13주차 자료와 팀 역할표(가짜 파일 수 10/100/1000, 응답 시간, 중앙값, 실행 조건)를 주고 "가짜 파일 생성 스크립트와 측정 스크립트, 실험 계획을 만들어 줘"라고 요청 |
| 결과 | `tests/make_decoys.py`(가짜 파일 생성·삭제), `tests/bench.py`(조건마다 서버 ③ 재실행 → 요청 3종 반복 측정 → 중앙값·평균·p95, 실행 조건 자동 기록), `docs/experiment_plan.md`, `.gitignore`에 생성 파일 등록 |
| 결과 확인 방법 | AI 환경 시험 실행(50회 × 2라운드): 이상 응답 0, 끝난 뒤 생성 파일 삭제·로그 복구 확인. 서버 ③이 일부러 진짜 파일을 주도록 바꿨을 때 이상 응답 10/10 검출. 내 PC의 Linux VM에서 소규모 실행(10·20개 × 10회): 이상 응답 0, `data/decoy/secret`에 passwords.txt만 남고 로그 원상복구 확인. **직접 확인:** Windows 11(10.0.26200), Python 3.14.3에서 `py tests/bench.py` 실행(200회 × 3라운드, 73.7초). 이상 응답 0. 같은 라운드 안에서는 가짜 파일 10/100/1000개의 중앙값 차이가 거의 없었고(라운드 2 공격 요청 5.1/5.0/5.3ms), 라운드 간 흔들림(약 4~15ms)이 훨씬 커서 파일 수의 영향은 없다고 판단. 공격·공격후정상이 정상보다 매 라운드 1~2ms 느렸으며, 로그 기록 때문으로 추정 |
| 채택·수정한 부분 | 처음 초안은 변수가 둘(허니패치 켬/끔 + 가짜 파일 수)이었으나 "변수는 하나" 기준에 맞춰 가짜 파일 수만 남김. 서버 실행 함수는 김진하의 `test_cases.py` 재사용. 평균이 튀는 값에 끌려가 대표값을 중앙값으로 정함. 실행이 강제 종료되면 가짜 파일·로그가 남는 문제가 생겨 SIGTERM에도 정리되도록 수정 |
| 막힌 점 | AI 환경 시험에서 라운드 간 흔들림(약 0.15ms)이 조건 간 차이와 비슷해 50회로는 부족 → 200회 × 3라운드로 정함. 내 PC의 VM(Windows 폴더 공유)에서는 파일 쓰기가 느려 응답 시간이 10~30ms로 부풀고 1000개 생성이 시간 초과 → 본 측정은 Windows에서 직접 실행. 로그를 쓰는 공격·공격후정상 요청이 정상보다 느린 경향이 보여 결과 해석 때 확인 필요 |

### 11/19 (목) — 서버 ③ 허니패치 구현 및 연동 확인

| 항목 | 내용 |
|---|---|
| 도구 | Claude |
| 요청 내용 | 저장소 구조 파악과 서버 ③ 구현 방향 검토, 연동 조건(로그 형식, X-Forwarded-For)과 내 구현의 차이 대조 |
| 결과 | `servers/honeypatch_server.py`, `data/decoy/secret/passwords.txt` 초안을 받아 직접 실행·검증 후 반영 |
| 결과 확인 방법 | 서버 ①②③과 `web/app.py`를 함께 띄워 위반 사례가 ① 유출 / ② 403 / ③ 가짜 파일로 나오는지 확인. 로그에 공격자만 기록되는지 확인. 기존 스모크 테스트 8/8 통과 |
| 채택·수정한 부분 | ②의 `check_path()`를 재사용해 ②③의 판정 기준을 통일. 로그 형식과 IP 판단을 비교 화면 명세에 맞춰 수정. 논문 동작을 반영해 공격 IP를 기억하는 sticky 기능 채택 |
| 막힌 점 | X-Forwarded-For는 위조 가능해 실제 환경에서는 신뢰할 수 없음. 원논문과 달리 요청 단위로 파일만 바꾸므로 파일 읽기 외의 공격은 격리하지 못함 |

### 11/21 (금) — 고정 사례 3종 자동 실행 및 ①②③ 비교

| 항목 | 내용 |
|---|---|
| 도구 | Claude |
| 요청 내용 | 원논문, 주차 자료, 작업 계획, 팀 저장소를 주고 "검증 사례 3개 자동 실행과 보호 적용 전·후 비교" 담당분을 구현해 달라고 요청 |
| 결과 | `tests/test_cases.py`(서버 ①②③을 빈 포트로 직접 띄워 고정 사례 3종을 보내고 응답 코드·진짜/가짜·미끼 전환·응답 시간을 비교), 결과 저장 파일 2종(`tests/results/results.md`, `results.json`), README 3-5절 |
| 결과 확인 방법 | 고정 사례 3종 × 서버 3개 = 9/9가 11주차 기대 결과표와 일치. 통과만 믿지 않고 ②③ 포트 자리에 일부러 ①(무방비) 서버를 물려 다시 실행 → 7/9로 떨어지고 `verdict 기대 fake / 실제 leak`처럼 어긋난 항목이 정확히 잡힘. 항상 통과하는 테스트가 아님을 확인 |
| 채택·수정한 부분 | 계획서의 requests+pytest 대신 표준 라이브러리(urllib)로 변경 — 저장소 전체가 추가 패키지를 쓰지 않아 재현 시 설치 단계를 없애기 위함(pytest로도 돌아가는 함수는 유지). 기대값을 코드 안 `CASES`에 고정해 실행 결과에 맞춰 바꾸지 못하게 함. 정상·경계는 10.0.0.10, 위반은 10.0.0.66으로 보내 서버 ③의 sticky(공격자 IP 기억) 때문에 생기는 오탐을 분리 |
| 막힌 점 | 응답 시간으로 ①과 ③의 차이를 보이려 했으나, 같은 서버 안의 측정 편차(1.4~24.6ms)가 서버 간 평균 차이(2.4ms)보다 커서 유의미한 비교가 되지 않음. 원논문의 지연 요인(메모리 치환·CRIU 프로세스 복제, 약 0.25초)을 본 구현이 갖고 있지 않기 때문이며, 성능이 좋다는 뜻이 아니라 비교 대상이 아니라는 뜻이라 한계로 기록 |
